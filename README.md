# MoneyLens · 个人收支与预算分析

把微信支付导出的账单 xlsx 变成一本能看的账：自动分类、月度趋势、预算预警、消费报告。
数据全部留在本机，不经过任何服务器。

## 快速开始

```bat
run.bat
```

它会解析账单、生成 `web/data.js`，然后用默认浏览器打开仪表盘。

单独执行其中一步：

```bash
python -m moneylens.build        # 解析 + 分析 + 生成数据与报告
start web/index.html             # 打开仪表盘（file:// 直接可用，无需服务器）
```

换一份账单：

```bash
python -m moneylens.build --src "C:\path\to\微信支付账单.xlsx"
```

运行测试：

```bash
python -m unittest discover -s tests -t .
node scripts/smoke_web.js
```

## 数据口径（这是本项目最容易被做错的部分）

微信账单不是干净的表格，四个坑必须显式处理：

**1. 退款是两条记录。** 原支出状态变成 `已退款(¥0.35)`，同时另加一条「智慧校园-退款」收入。
如果两条都算，支出和收入同时虚增。本项目的做法是：**只认原支出状态里的退款金额**，退款腿净额记为 0。

```
净支出 = 原始金额 − 状态中标注的退款金额
全额退款（已全额退款 / 对方已退还）→ 退款 = 原始金额
```

**2. 还款不是消费。** 「美团金融还款」被微信标成支出，但钱在借款时已经花过，计入就是重复统计，
归入 `settlement`，两种口径都不参与。

**3. 转账不是消费。** 转账、红包、群收款单列为 `transfer`，只出现在现金流里，不进入消费分析。

**4. 首尾月份不完整。** 本账单 7 月从 21 日开始、10 月到 21 日结束。跨月比较一律用**日均**
（消费 ÷ 该月实际覆盖天数），预算则按「已用 ÷ 已过天数 × 当月天数」外推月末。

统计口径：

| 指标 | 定义 |
| --- | --- |
| 消费净额 | 支出净额，不含转账、还款、中性交易 |
| 收入净额 | 收入净额，不含退款腿 |
| 转账净额 | 转入 − 转出，单独展示 |
| 净结余 | 收入 + 转入 − 消费 − 转出 |

中性交易（充值/提现/零钱通划转）由微信标为 `/`，Excel 里没有方向，解析时归为 `neutral`。

## 分类：四层优先级

1. **人工覆盖** `overrides.json` —— 人确认过的，永远最高
2. **规则引擎** `rules.json` —— 只写行业词（超市、面馆、卫生室、充电…），可解释、可测试
3. **AI 建议** `ai_suggestions.json` —— 规则覆盖不到的长尾商户，AI 给候选并标 `source=ai`
4. **待确认** —— 个人收款码的商户名是昵称（「艾稀宇」「王艳庆」），规则和 AI 都不可靠，
   不猜，进队列交给人在界面上点

仪表盘右侧的「待确认分类」就是这个队列。确认一条，所有图表立刻按新分类重算。

确认结果可以通过「导出确认」下载，再回写：

```bash
python scripts/apply_confirmations.py moneylens-confirmations.json
```

## 校验与质量

- **解析校验**：逐项比对微信自报的「收入/支出/中性交易」笔数与金额，必须完全一致才继续。
  这能防住表头错位、漏行、金额被当成文本之类的静默错误。
- **口径闭合测试**：消费净额 = 支出净额 − 转账转出 − 还款，任何一项算错都会被发现。
- **分类覆盖率**：自动分类覆盖 90.4%，剩余 19 笔个人收款码进待确认、12 笔未匹配。
  这个比例就是分类质量的度量，会写进报告。

## 技术取舍

- **零依赖前端**：手写 SVG 图表而不是引 ECharts/Chart.js。原因是演示要能双击 `index.html`
  直接打开，不依赖网络与构建工具；代价是图表能力有限（只有柱、环、面积三种）。
- **Decimal 而非 float**：金额聚合全部用 `Decimal`，避免 `0.1 + 0.2` 这类误差在月度汇总里放大。
- **构建与展示分离**：Python 负责解析、分类、生成报告；浏览器负责按当前筛选与人工确认实时重算。
  两边各算一次，测试里用「口径闭合」保证结果一致。
- **本地优先**：人工确认、手动记账、预算调整都存在 `localStorage`，同时可以导出回写，
  不依赖后端服务。

## 已知边界

- 只解析微信支付账单的 xlsx 格式，不处理支付宝/银行流水（结构不同，但 `ingest` 可以按同样的模式扩展）。
- 分类规则是按这份账单的商户分布写的，换一个人用会需要补规则——这正是「待确认队列」存在的原因。
- 预算目前是「分类 × 月度」，没有做年度预算与结转。
